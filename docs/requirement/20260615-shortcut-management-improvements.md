# 快捷方式管理改进

- Flow mode: strict
- Stage: Requirement
- Review status: Accepted
- Date: 2026-06-15

## Background

当前快捷方式管理存在几个问题：

1. 快捷方式存储仍在 `terminals.json` 的扁平列表中，不利于按运行环境隔离管理、按名称定位和删除校验。
2. 前端删除按钮依赖组件传入的会话列表推导快捷方式是否被使用，容易和真实后端状态不一致。
3. 删除是否允许应由快捷方式查询结果和后端删除校验共同保证，而不是依赖 `openTerminalSessions` 或前端临时计算。
4. 编辑能力需要随新存储模型和使用计数语义一起检查，避免编辑后破坏名称唯一性、分组展示或删除判断。
5. 旧数据可以通过一次性迁移处理；迁移完成后的业务逻辑不需要继续兼容旧的 `terminals.json` 快捷方式存储。

本需求从存储模型入手重做快捷方式管理的数据结构、接口返回和前端判断方式。由于涉及存储结构、API 合约、前端类型和会话引用关系，流程模式使用严格模式 / strict，后续需要补充 Spec / 规格阶段。

## Goals

1. 将快捷方式从 `terminals.json` 拆出到新的 `shortcuts.json`。
2. 将快捷方式存储调整为两级结构：一级为运行环境，二级为快捷方式名。
3. 快捷方式保留并生成稳定 `id`，以便会话记录引用快捷方式。
4. 查询快捷方式接口返回按运行环境分组的两级快捷方式列表，并为每个快捷方式添加 `used_session_count` 字段。
5. `used_session_count` 由后端基于实际 session storage 统计得出。
6. 前端直接使用接口返回的两级结构渲染分组，并根据 `used_session_count` 判断是否允许删除，不再基于 `openTerminalSessions`、传入会话列表或前端二次分组计算推导。
7. 后端删除快捷方式时必须再次校验实际会话引用，防止绕过前端直接删除被会话引用的快捷方式。
8. 编辑快捷方式功能在新模型下保持可用，保存后列表、分组、使用计数和删除状态正确刷新。
9. 删除快捷方式功能在新模型下可用，未被会话使用的快捷方式可删除，被使用的快捷方式不可删除并给出明确反馈。
10. 提供一次性数据迁移：读取旧 `terminals.json` 中的快捷方式数据，重新生成新的 `shortcuts.json`。
11. 迁移完成后的业务读写逻辑不再使用 `terminals.json` 管理快捷方式，也不向后兼容旧快捷方式格式。

## Non-goals

1. 不在业务代码中长期兼容旧的 `terminals.json` 扁平 `shortcuts: []` 存储格式。
2. 不继续依赖 `openTerminalSessions` 判断快捷方式是否被使用。
3. 本轮不实现快捷方式拖拽排序。
4. 不实现跨环境移动快捷方式。
5. 不引入额外数据库；仍使用本地 JSON 文件作为存储。
6. 不重新设计会话创建流程，只保证新建会话读取和提交快捷方式时兼容新的存储和引用方式。
7. 不将快捷方式继续存储在 `terminals.json`。
8. 不要求迁移逻辑长期保留为运行时兼容分支；迁移是一次性数据转换。

## User scenarios

1. 用户打开快捷方式管理页，可以按 Cygwin、WSL、Linux 等运行环境看到分组后的快捷方式。
2. 用户删除一个未被任何会话引用的快捷方式，删除成功，列表刷新后该快捷方式消失。
3. 用户尝试删除一个已被会话引用的快捷方式，前端根据 `used_session_count` 禁用或阻止操作，并展示“使用中”含义；即使绕过前端调用删除接口，后端也拒绝。
4. 用户编辑快捷方式名称、命令、说明或运行环境相关字段后，保存成功并刷新列表。
5. 用户编辑快捷方式时，如果新名称在同一环境下重复，应被前端校验和/或后端校验拦截。
6. 用户在不同环境下可以使用相同快捷方式名称，因为同环境内名称唯一即可。
7. 用户在新建会话界面选择快捷方式时，仍能看到按当前运行环境可用的快捷方式，并能基于快捷方式 `id` 创建会话。
8. 开发者或维护者执行一次性迁移后，旧 `terminals.json` 的扁平快捷方式数据被转换为新的 `shortcuts.json`；迁移后的应用按 `shortcuts.json` 运行。

## Acceptance criteria

1. 快捷方式存储文件为 `shortcuts.json`，不再是 `terminals.json`。
2. `shortcuts.json` 中快捷方式以两级结构保存：环境 -> 快捷方式名 -> 快捷方式数据。
3. 新存储结构中的快捷方式数据包含稳定 `id`。
4. 新建快捷方式时后端生成唯一 `id`。
5. 会话记录继续通过快捷方式 `id` 引用快捷方式。
6. 查询快捷方式接口返回按运行环境分组的两级快捷方式列表，每个快捷方式包含 `used_session_count` 字段。
7. `used_session_count` 来自后端基于实际 session storage 的统计，而不是前端临时计算。
8. 前端快捷方式管理页直接使用接口返回的两级结构渲染分组，不再自己计算分组。
9. 前端快捷方式管理页删除判断只依赖接口返回的 `used_session_count`。
10. 前端快捷方式管理页不再需要从 `AppShell` 接收 `sessions` 仅用于计算快捷方式占用状态。
11. 后端删除接口在删除前校验实际会话引用；使用中的快捷方式删除请求必须失败。
12. 未使用快捷方式删除成功后，后端存储和前端列表都移除该快捷方式。
13. 编辑快捷方式保存成功后，后端存储更新，前端列表刷新展示新值。
14. 同一环境下快捷方式名称保持唯一；编辑时不能把名称改成同环境已有名称。
15. 不同环境下允许存在相同快捷方式名称。
16. 新建会话表单仍能按选择的运行环境过滤和选择快捷方式。
17. 新建会话提交时继续使用快捷方式 `id`，后端能正确解析目标快捷方式。
18. 一次性迁移能读取旧 `terminals.json` 中的快捷方式数据并生成新的 `shortcuts.json`。
19. 迁移完成后的正常业务读写路径不继续使用 `terminals.json` 中的快捷方式数据。
20. 删除和编辑在浅色和暗色主题下保持可用且状态清晰。
21. 本轮实现不包含快捷方式拖拽排序入口、接口或持久化逻辑。

## Decisions

1. 使用严格模式 / strict。
   - Why: 涉及存储结构、API 合约、会话引用标识、一次性迁移和前端交互，需要先进入 Spec / 规格阶段明确设计。
2. 使用字段名 `used_session_count`。
   - Why: 用户明确指定该字段名，且语义直接表达“当前引用该快捷方式的会话数量”。
3. 快捷方式保留并生成稳定 `id`。
   - Why: 用户明确指出保留 `id` 更适合会话引用。
4. 快捷方式从 `terminals.json` 拆出到 `shortcuts.json`。
   - Why: 用户明确要求直接读取旧 `terminals.json` 并重新生成 `shortcuts.json`，后续不再使用 `terminals.json` 管理快捷方式。
5. 做一次性迁移，但业务逻辑不向后兼容旧快捷方式格式。
   - Why: 用户明确要求“一次性迁移数据即可，不在业务上向后兼容”。
6. 本轮排序先不实现。
   - Why: 用户明确调整范围为“排序先不实现”，避免扩大实现范围。
7. 删除是否允许以服务端统计的 `used_session_count` 和删除接口实际引用校验为准。
   - Why: 前端无法可靠从打开的终端 tab 或局部会话列表判断全局引用关系。
8. `TerminalService` 可以注入 session repository。
   - Why: 用户明确选择“注入”，用于统计使用计数和删除校验。

## Open questions

暂无需要用户确认的未决事项。

后续 Spec / 规格阶段需要设计但不需要用户先确认的细节：

1. `shortcuts.json` 的两级结构中，`id`、`command`、`description` 等字段如何编码。
2. 编辑快捷方式名称时，如何处理 `host -> name` key 的迁移与同环境名称唯一校验。
3. 一次性迁移入口、覆盖策略和是否生成备份。
4. 从 `terminals.json` 拆出快捷方式后，`terminals.json` 是否只保留 terminal settings / environment settings，或后续另行重命名。

## Risks / Assumptions

1. `id` 虽保留用于会话引用，但存储 key 是 `host + name`，需要保证编辑名称时 `id` 不变且 key 正确迁移。
2. 以快捷方式名作为二级 key 时，重命名快捷方式等同于 key 迁移，需要在保存逻辑中保证原 key 删除、新 key 写入的原子性。
3. 一次性迁移会写本地状态文件，必须明确运行时机和验证方式，避免误改用户已有配置。
4. 删除校验需要读取 session storage，会让 terminal/shortcut service 与 session repository 的依赖关系更紧密；用户已接受注入方案，但实现仍需避免循环依赖。
5. 新建会话表单、快捷方式管理页和后端接口共享快捷方式类型，字段变更需要同步更新 TypeScript 类型和 Python models。
6. 因为业务逻辑不向后兼容旧快捷方式格式，未执行迁移或迁移失败会导致快捷方式读取失败；Verification 阶段需要覆盖迁移成功后的新格式路径。
